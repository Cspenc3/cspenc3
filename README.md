## How I Think

I enjoy understanding systems, not just fixing symptoms. My approach usually begins with four questions:

1. **What should be happening?** Understand the system and its intended behavior.
2. **What is actually happening?** Collect evidence before jumping to a conclusion.
3. **What else could explain it?** Consider dependencies, failure modes, risk, and competing hypotheses.
4. **How do we know a change worked?** Validate it, measure its impact, and document the result.

I value **systems thinking, intellectual humility, and decisions grounded in evidence**. I'm especially interested in the difference between an operational failure and a security incident—and how an engineer can tell them apart.
